System Architecture · Built

Autonomous Job-Search Pipeline

A locally-powered pipeline that reads your documents into a structured profile, scouts job boards with Playwright, scores every new posting against that profile, and keeps you and your inbox in sync — without you touching a spreadsheet, or paying for an API key.

LLM Ollama (qwen2.5:1.5b, local, free) Email Gmail API (OAuth) Scraping Playwright, adapter-per-site Language Python 3.11+ Status code running, 25/25 tests passing — awaiting your documents & credentials

How data moves through the system

One setup pass turns your paperwork into profile.json. Everything after that runs on a loop: scrape → score against the profile → dedupe against history → notify → watch the inbox for replies.

Modules

Seven small, independently testable pieces. Each one has a single job and a typed input/output — swapping a job site or an email provider later means replacing one module, not the pipeline.

01 · Setup pass

Ingestion

Watches a local /inbox folder for anything you drop in — PDFs, DOCX, scanned images of diplomas or reference letters. Runs OCR on images/scanned PDFs, extracts raw text from native PDFs and DOCX.

in files → out raw text + source metadata
02 · Setup pass

Extraction Engine

Sends raw text to a local Ollama model (default qwen2.5:1.5b) with output grammar-constrained to a JSON schema that is the candidate profile — education, certifications, work history, skills, languages — with a validate-and-retry loop for a small model's occasional misses. You review and correct the draft once before it's trusted for matching.

in raw text → out profile.json
03 · Loop

Scraper

One adapter class per source, same interface: fetch(query, location) → JobPosting[]. Targets: StepStone, Indeed, jobvector, LinkedIn — filtered to Life Science/QC and coding/data-science roles. All four are scrape-only in 2026; see the compliance note below before running against them.

in search config → out raw postings
04 · Loop

Matcher

The local Ollama model compares each new posting against profile.json and returns a score, the reasons for it, and what's missing — not just a yes/no. Threshold is configurable, so you tune sensitivity instead of me guessing it.

in profile + posting → out match_result.json
05 · Loop

Tracker

A small SQLite database that remembers what you've already seen. This is what stops the same posting from emailing you twice, and what turns raw matches into a lifecycle: discovered → notified → applied → responded → closed.

in matches + thread updates → out current state
06 · Loop

Email Agent

Two-way with Gmail. Outbound: sends you a plain-language digest of new high-scoring matches. Inbound: polls the inbox for recruiter replies or interview requests tied to tracked applications and asks the local model to summarize and file the status update.

in/out Gmail (OAuth, scoped)
07 · Loop

Scheduler

Runs the loop — scrape, match, notify, poll inbox, update tracker — on an interval you set (e.g. every 4 hours), then sleeps. Owns the run config: search queries, locations, score threshold, cadence.

owns config.yaml + run cadence

Read before running the scraper against these four sites

None of StepStone, Indeed, jobvector, or LinkedIn offer a compliant search API

Checked all four as of August 2026: Indeed's public Publisher API and XML feed were both retired in 2024 — the only remaining Indeed integrations are enterprise partner programs requiring a sales process. StepStone and jobvector have never published a public search API; their listings are reachable without login, but that doesn't imply a right to automate against them — it just means no CAPTCHA-walled login to defeat. LinkedIn is the clearest documented case: its Terms of Service prohibit scraping regardless of whether the data is public, and LinkedIn won hiQ v. LinkedIn on exactly that breach-of-contract ground, and is currently pursuing a similar suit against the scraping service Proxycurl. For an individual, the practical risk on any of the four isn't a lawsuit — it's the site's bot-detection flagging the account and restricting or banning it.

Given that, the adapters are ordered by rising risk, not alphabetically:

  • StepStone & jobvector first — no public precedent of enforcement against individual scrapers found, but still ToS-prohibited; keep request volume low and add delays regardless.
  • Indeed next — same posture, plus Indeed is known to actively rate-limit and CAPTCHA aggressive traffic.
  • LinkedIn last, and lowest-frequency — the one with documented enforcement, so it runs least often and against an account you're comfortable seeing restricted, never the one you apply from.
  • Optional low-risk supplement — Adzuna, USAJobs, RemoteOK, and most company career pages (Greenhouse, Lever, Workday) do expose real ToS-compliant APIs; the adapter interface supports adding one alongside the four scrapers if you ever want extra coverage without extra risk.

One EU-specific note: StepStone and jobvector are Germany-based, so GDPR applies. Job listings themselves aren't personal data, but a posting's named recruiter contact (name + direct email) can be — the scraper should keep only what's operationally needed (title, company, location, description, URL) and skip persisting recruiter contact fields.

Every adapter now walks the full results listing for a search — scraping/base.py's paginate_search() requests page 2, 3, ... directly by URL (?page=N, or each site's offset param) instead of reading only the first page, so a single search can trigger several page-loads. That's more requests per search on all four sites, LinkedIn included — factor that into request-volume judgment calls above rather than assuming each search is still a single page fetch. search.max_postings_per_search in config.yaml (default null = no cap) stops a search early once that many postings are collected, trading completeness for fewer requests.

LinkedIn's own job-link pattern was also wrong (matching zero real links — its adapter was silently returning ~0 postings every run) and, once fixed, surfaced a shared bug in nearest_card_text(): a non-matching ancestor selector auto-waited Playwright's full 20s default per attempt, which a live run measured as a 9+ minute stall on LinkedIn's DOM specifically. Both fixed and confirmed live — see the README's Compliance note for the measured before/after.

Defaults I've decided, so you don't have to

Every one of these lives in config.yaml and is a one-line change later. Where a decision affects account-ban risk or inbox noise, I optimized for the safer, quieter option rather than the fastest one.

DecisionDefaultReasoning
Scrape cadence2×/day — 09:00 & 18:00 localMatches a human checking job boards morning/evening; a 4-hour poll is easy for bot-detection to fingerprint as automation
Match thresholdscore ≥ 70/100High enough to filter noise, low enough not to miss a good-but-imperfect fit; the reasons/missing fields let you eyeball anything near the cutoff
Notification batchingOne digest email per run, not per jobA run with 6 matches becomes 1 email, not 6 — protects the inbox from becoming the thing you have to triage
Dedupe keysha256(company+title+location), normalizedRaw URLs break dedup — tracking params and re-listings change the URL without changing the job
Source adaptersStepStone, jobvector, Indeed, LinkedIn — run in that order; LinkedIn additionally capped at once per 24h regardless of scheduler frequencyNone of the four expose a public search API in 2026 (Indeed's was retired outright), so all four are scrape adapters; ordered by rising enforcement risk — see compliance note
Search preferenceTwo target domains, either qualifies: Life Science & Quality Control or Coding & Data ScienceBaked into the Matcher's scoring prompt directly — a posting outside both domains scores low regardless of surface keyword overlap
Document folder./data/inbox/ — subfolders are cosmetic, everything in the tree gets processedOne drop point, no upload flow to build for a single-user tool
OCR triggerOnly runs if native text extraction yields < 50 charactersMost diplomas/CVs are native-text PDFs; OCR is slower and lossier, so it's a fallback, not the default path
Email scopesgmail.readonly + gmail.send onlyNever requests gmail.modify/delete — the agent can read and notify, never alter your mailbox

What still has to come from you

The repo is built and tested (25/25 passing) — these two are the only pieces that were never mine to decide.

  1. Documents — drop diplomas, CV, and reference letters into data/inbox/ (subfolders cv/, diplomas/, references/, other/ exist and are cosmetic — everything in the tree gets processed either way).
  2. Credentials — none for the LLM (Ollama runs locally, no key); just a Google OAuth client secret saved to data/google_credentials.json for Gmail. The one-time consent-screen click has to be you, by design — that's what makes the access revocable.
